# Проект, checkout и начало задачи

Читай при адаптации или выборе места работы. `workdir/project.json` соответствует [схеме](../schemas/project.schema.json). Все пути модели относительно явно переданного project root, кроме target.path относительно repository. Symlinks разрешены только внутри соответствующей границы.

Repository ID сохраняет namespace, например `ticketon-fho/frontend/afisha`. `path` указывает на Git root основного рабочего clone; `references` перечисляет защищённые reference-каталоги, включая независимые clones с тем же remote. Изменяющая задача выбирает зарегистрированный task worktree этого clone. Чтение reference допустимо; запись и Worktrunk-операции над ним запрещены.

Target связывает приложение с repository и путём внутри него. Несколько targets могут принадлежать одному repository. Реестр проверяет безопасный относительный путь target без требования его наличия в основном clone. Существование, физические границы repository и локальные инструкции target проверяются в выбранном worktree; инфраструктуру соседней ветки не заимствуют. Текущие worktrees и HEAD получаются из Git, а не из постоянной копии списка.

`development` — закреплённое имя ветки. Release имеет `fixed`, `date` или `semver` policy. Date использует `release-YYYY-MM-DD`, semver — три числовых компонента `release-X.Y.Z`; иное соглашение требует явного развития схемы. Семейство не выбирает активный релиз. Все ветки, соответствующие объявленному release-семейству, защищены от выбора как task-ветки, независимо от purpose и выбранной базы; исправление выполняется в отдельной task-ветке. Для release-задачи передай конкретную существующую ветку; не выбирай максимальную дату/версию. Перед изменениями проверь актуальность базы с remote в рамках разрешённой работы. `inspect` использует локальные branches и не обновляет их.

Worktrunk владеет шаблонами путей и lifecycle-конфигурацией. `tools.worktrunk.config` задаёт существующий project-relative config или null для нативного эффективного конфига. При required wt отсутствие инструмента блокирует создание/выбор изменяющего workflow; fallback не выполняется молча. Сначала переиспользуй подходящий worktree, иначе создай стандартной командой wt с явной базой и используй путь результата. Не удаляй worktrees без проверки сохранности изменений и commits.

Graphify: `enabled` означает выбор инструмента, не его установку и не актуальность графа. `procedure` указывает проектный документ, определяющий область, команду, exclusions и provenance. Перед использованием сравни источник и revision с выбранным checkout. Отсутствие ребра не доказывает отсутствие зависимости. Не устанавливай hooks автоматически. `inspect` при enabled проверяет наличие executable в PATH, но не запускает Graphify и не угадывает расположение графа. После чтения procedure выполни `npm run inspect:graph -- <selected-root> <relative-graph-path> [command]`: команда раздельно сообщает executable-found/missing, present/missing графа и freshness unknown. command допускает имя в PATH или абсолютный путь к проектному wrapper. Проверяются JSON-синтаксис, граница root и hash; семантика формата и работоспособность CLI не утверждаются. Актуальность устанавливается по проектной процедуре и исходникам, не по mtime. Для task-графа selected-root — текущий worktree; workspace-граф проверяется отдельно с его root и не выдаётся за task-граф.

Подключения E2E/Design содержат локальный путь и точный commit. Их targets ссылаются на этот реестр, предметные настройки остаются у соответствующего манифеста. Нельзя копировать browser profiles, design snapshots или архитектурные нормы в Project Manifest. В самостоятельном E2E/Design режиме реестр target может быть локальным; при интеграции выбирается один владелец.

Примеры требований, не общие defaults: Ticketon сохраняет GitLab namespace и раздельные source/deploy-config repositories; Korner запрещает изменять `korner-gh/`, создавая task worktrees из рабочих clones. FSD Korner и собственные правила Afisha не объединяются.

## Проверка Worktrunk

`npm run test:worktrunk` требует установленный `wt`. Проверено на 0.74.0: отдельный локальный проект, обязательный wt, workspace-конфигурация через `--config`, development и конкретная semver release-база с разными commits. Тест потребляет `path` из `wt switch --format json`, затем передаёт его `planTask`; шаблон пути не копируется в модель. Повторный switch после изменения шаблона сохраняет существующий worktree. Отсутствующая база не создаёт другой checkout; основной clone и неопределённый активный release отклоняются.

В рабочей процедуре сначала прочитай применимые инструкции и конфигурацию. Для создания используй `wt --config <absolute-config> -C <working-clone> switch --create <task-branch> --base <chosen-base> --format json`; при config=null используй эффективную нативную конфигурацию без этого флага. Для существующего task worktree не добавляй `--create`. Полученный путь — вход проверки target, а не повод переключать основной checkout. Формат и параметры сверяй с установленной версией и [официальной документацией](https://worktrunk.dev/config/).

Probe отключает hooks только в синтетическом fixture и не проверяет remote или lifecycle hooks. Его `worktrunk-verification.json` сохраняется в выбранном target/e2e/tmp, worktrees остаются для инспекции. Обычный `inspect` проверяет регистрацию Git и доступность обязательного wt; он не может ретроспективно доказать, какой командой создан произвольный worktree.
